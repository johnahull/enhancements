## Overview

This VEP defines VM-scoped persistence for Kubernetes Dynamic Resource
Allocation (DRA) ResourceClaims used by KubeVirt.

A user declares a ResourceClaim once in the `VirtualMachine` template. The
claim may be a manually-created direct claim, a claim generated from a
`ResourceClaimTemplate`, or a managed claim generated by a VEP-300 provisioner.

KubeVirt resolves each declaration to a concrete `ResourceClaim` and adds the
VM as a consumer in `ResourceClaim.status.reservedFor`. The VM reservation is
retained across VMI and launcher Pod replacement. A common reservation
controller handles all claim sources; claim creation remains source-specific.

Standalone VMIs retain their existing VMI-scoped behavior.

## Motivation

DRA claims are normally consumed by Pods. KubeVirt creates and deletes
launcher Pods as VMIs are started, stopped, restarted, or recovered. If a
claim is reserved only for the launcher Pod, deleting that Pod can release the
allocation before the replacement Pod is scheduled.

Releasing and reallocating the device can cause:

1. A VM to receive a different GPU, host device, or network device after a
   restart.
2. Device-specific state or data to become unavailable.
3. Network identity, such as a MAC address or DHCP reservation, to change.
4. A restart to fail because another workload acquired the device during the
   allocation gap.

The VM, rather than the launcher Pod, is the logical owner of a device attached
to the VM. The VM therefore needs to be represented as a DRA claim consumer.

## Goals

- Retain VM-scoped DRA allocations across VMI and launcher Pod replacement.
- Support direct, ResourceClaimTemplate-backed, and managed claims.
- Require users to declare a VM claim only once in the VM template.
- Use one reservation and cleanup mechanism for all VM-scoped claim sources.
- Allow users to choose whether an allocation is retained across an explicit
  VM stop.
- Preserve existing standalone VMI claim behavior.
- Keep managed claim generation in the VEP-300 provisioner.
- Prevent KubeVirt from modifying or deleting user-owned direct claims.
- Clean up KubeVirt-owned reservations during VM deletion.

## Non Goals

- Changing Kubernetes DRA allocation or scheduling behavior.
- Supporting live migration of DRA-backed devices.
- Eagerly allocating claims for halted VMs.
- Defining device-specific request semantics owned by VEP-152, VEP-183, or
  other device-specific proposals.
- Changing the managed claim generation model defined by VEP-300 beyond the
  additions required for VM scope.
- Mutating an allocated `ResourceClaim.spec` in place.
- Defining a general-purpose shared-claim policy for multiple VMs.

## Definition of Users

- **VM user:** A person who declares devices in a VirtualMachine template.
- **VMI user:** A person who creates and manages a standalone
  VirtualMachineInstance.
- **Cluster administrator:** A person who installs DRA drivers and configures
  ResourceClaimTemplates or managed claim provisioners.
- **Provisioner author:** A person who implements a VEP-300 managed claim
  provisioner.

## User Stories

- As a VM user, I want a GPU allocation to survive VM restart so that the VM
  receives the same device after its launcher Pod is recreated.
- As a VM user, I want to declare a direct claim, template-backed claim, or
  managed claim in one place.
- As a VM user, I want to release a device on explicit stop when resource
  efficiency is more important than device stability.
- As a VM user, I want to retain a device on explicit stop when the device has
  persistent state or identity requirements.
- As a cluster administrator, I want generated claims to be owned by the VM
  that uses them.
- As a provisioner author, I want the managed claim framework to identify
  whether a claim belongs to a VM or a standalone VMI.
- As a KubeVirt developer, I want the generated VMI to be an implementation
  detail rather than a second user-facing claim configuration surface.

## Design

### Design Principle

Claim provisioning and claim persistence are separate concerns:

```text
VM template claim entry
        |
        v
claim source resolver
        |
        v
concrete ResourceClaim
        |
        v
DRA allocates the claim for the launcher Pod
        |
        v
common VM reservation controller maintains status.reservedFor
```

There must not be one persistence implementation for direct claims, another
for template-backed claims, and another for managed claims. The source-specific
code only resolves or creates the concrete claim. The VM reservation controller
then applies the same lifecycle rules to every VM-scoped claim.

### Feature Gate

All VM-scoped claim behavior is gated behind `PersistentDRAClaims` during
alpha. The feature gate controls the new API validation, VM reservation
reconciliation, VM finalizer behavior, and VM-scoped ResourceClaimTemplate
materialization.

### API Changes

The API uses an internal scope type for the managed-claim framework. Scope is
inferred from the owning object; users do not set this field directly:

```go
type ResourceClaimScope string

const (
	ResourceClaimScopeVMI ResourceClaimScope = "VMI"
	ResourceClaimScopeVM  ResourceClaimScope = "VM"
)
```

The existing `VirtualMachineInstanceResourceClaim` entry is extended with
`persistWhenStopped`:

```go
type VirtualMachineInstanceResourceClaim struct {
	// Name uniquely identifies this claim inside the VM or VMI.
	Name string `json:"name"`

	// Exactly one of ResourceClaimName,
	// ResourceClaimTemplateName, or ManagedClaimProvisionerName must be set.
	ResourceClaimName *string `json:"resourceClaimName,omitempty"`

	ResourceClaimTemplateName *string `json:"resourceClaimTemplateName,omitempty"`

	ManagedClaimProvisionerName *string `json:"managedClaimProvisionerName,omitempty"`

	// PersistWhenStopped controls whether the VM reservation is retained after
	// an explicit VM stop. It does not control VMI or launcher Pod replacement.
	// VM reservations are always retained across restart and recovery.
	// +optional
	PersistWhenStopped *bool `json:"persistWhenStopped,omitempty"`
}
```

The VM user declares the entry once in:

```text
VirtualMachine.spec.template.spec.resourceClaims
```

The VMI generated from the template may contain a copied claim entry, but the
VM template is authoritative. Users do not maintain a second claim entry on
the VMI.

The current `VirtualMachineSpec.resourceClaimTemplates` API proposed by the
initial VEP design is not used by this design. A ResourceClaimTemplate is
referenced through the existing claim entry instead.

### Scope Determination

Scope is inferred from the object containing the declaration:

| Declaration location | Scope | Lifecycle owner |
|---|---|---|
| `VirtualMachine.spec.template.spec.resourceClaims` | VM | VirtualMachine |
| `VirtualMachineInstance.spec.resourceClaims` | VMI | VirtualMachineInstance |

No `scope` field is required for the normal VM use case.

When a VM creates a VMI, the copied VMI entry must not cause a second
VMI-owned claim to be created. Controllers determine whether a VMI belongs to
a VM and process the VM template as the authoritative source.

### Direct Claims

For a direct claim:

- KubeVirt resolves `resourceClaimName`.
- The claim must be in the VM's namespace.
- KubeVirt never changes the claim spec.
- KubeVirt never deletes the claim.
- KubeVirt adds and removes only its VM consumer reference.

The user remains responsible for creating and deleting the direct claim. If
the claim is already reserved for an incompatible consumer, the VM reports a
reservation conflict and does not start.

### ResourceClaimTemplates

For a VM-scoped `resourceClaimTemplateName`:

1. KubeVirt reads the ResourceClaimTemplate.
2. KubeVirt creates one concrete ResourceClaim for the VM.
3. The concrete claim receives a controller owner reference to the VM.
4. The launcher Pod references the concrete claim name.
5. The common VM reservation controller manages the VM reservation.

The launcher Pod must not reference the ResourceClaimTemplate directly. This
prevents the claim from being tied to the lifetime of an individual launcher
Pod. Kubernetes ResourceClaimTemplate-generated claims are normally associated
with the consuming Pod; VM scope requires a stable direct ResourceClaim.

The generated claim is created lazily when the VM starts. It is retained as an
object for the VM lifetime, but its allocation may be released when
`persistWhenStopped` is false. This makes the policy about allocation
retention, not about whether a generated object exists.

### Managed Claims

VEP-300 is extended to support managed claims originating from a VM template.

For a VM-scoped managed claim:

- the managed claim provisioner watches the VirtualMachine;
- device declarations are read from `spec.template.spec`;
- the generated ResourceClaim is owned by the VM;
- the generated ResourceClaim name is stable across VMI replacement;
- the managed claim provisioner creates and maintains the claim spec;
- virt-controller renders the generated claim name into the launcher Pod;
- the common VM reservation controller maintains `status.reservedFor`.

Virt-controller does not invoke the provisioner and does not generate the
managed ResourceClaim spec.

VEP-300's managed claim context is extended to identify the owning workload:

```go
type ManagedClaimContext struct {
	VM          *v1.VirtualMachine
	VMI         *v1.VirtualMachineInstance
	Claim       *v1.VirtualMachineInstanceResourceClaim
	Provisioner *v1alpha1.ManagedClaimProvisioner
	Devices     ManagedClaimDevices
}
```

For a VM-scoped claim, `VM` is populated and the VM template is authoritative.
For a standalone VMI claim, `VMI` is populated and the existing VEP-300
behavior is preserved.

The managed claim framework must watch both VirtualMachines and standalone
VMIs. It must skip the VMI provisioning path for a VMI generated from a VM
template, preventing duplicate claims.

VEP-300 should add a capability declaration to `ManagedClaimProvisioner` so a
VM-scoped request can fail early when the provisioner does not support it:

```go
type ManagedClaimProvisionerSpec struct {
	Provisioner    string                  `json:"provisioner"`
	DeviceTypes    []ManagedClaimDeviceType `json:"deviceTypes"`
	SupportedScopes []ResourceClaimScope   `json:"supportedScopes,omitempty"`
}
```

When `supportedScopes` is omitted, the provisioner supports only VMI scope for
backward compatibility.

### Claim Naming and Ownership

Direct claims retain their user-provided name.

Generated VM-scoped claims use a deterministic name based on the VM name and
logical claim name:

```text
<vm-name>-<claim-name>
```

The naming algorithm must apply the Kubernetes DNS length limit and use a hash
when truncation is required. The owner UID must be included in labels and
verified before an existing generated claim is adopted.

VM-scoped generated claims have a controller owner reference to the VM. They
also carry labels identifying the logical claim and source:

```yaml
kubevirt.io/resource-claim: <claim-name>
kubevirt.io/resource-claim-scope: VM
kubevirt.io/resource-claim-vm: <vm-name>
kubevirt.io/resource-claim-source: template|managed
```

The managed claim provisioner and virt-controller must use the same naming
function. A generated claim with the expected name but a different owner UID
must not be adopted or overwritten.

### Launcher Pod References

For VM-scoped claims, the launcher Pod always references a concrete
`resourceClaimName`.

The Pod does not reference a `resourceClaimTemplateName`, and it does not need
to know whether the concrete claim was direct, template-backed, or managed.

### VM Reservation

After the claim has been allocated, KubeVirt adds a consumer reference for the
VM to `ResourceClaim.status.reservedFor`.

The VM reference contains:

- API group: `kubevirt.io`;
- resource: `virtualmachines`;
- namespace;
- VM name;
- VM UID.

The reservation controller must:

- add the VM reservation for every VM-scoped claim, regardless of
  `persistWhenStopped`;
- retain the reservation across VMI and launcher Pod replacement;
- preserve Pod and other consumer references;
- update the claim with conflict retries;
- avoid adding a VM reservation before the claim is allocated;
- remove only the VM's own reservation.

The `persistWhenStopped` setting controls what happens during an explicit VM
stop. It does not control whether the VM reservation is used during normal
running, restart, or recovery.

There is a small unavoidable race between DRA allocation and the first VM
reservation update because Kubernetes does not allow a reservation for an
unallocated claim. KubeVirt must minimize this window and ensure the VM
reservation is installed before deleting a launcher Pod for an intentional
stop. The implementation must report reservation failures and retry them.

### Explicit Stop

When a VM is explicitly stopped:

- `persistWhenStopped: true`: retain the VM reservation and allocation;
- `persistWhenStopped: false` or unset: remove the VM reservation.

When the VM reservation is removed and no other reservation remains, the DRA
controller may deallocate the claim. A generated claim object may remain and
be reallocated on the next start. A direct claim remains entirely user-owned.

### VM Deletion

KubeVirt adds a VM finalizer while VM-scoped claim reservations exist.

During VM deletion:

1. KubeVirt removes the VM from every VM-scoped claim's `reservedFor`.
2. KubeVirt retries until the reservation is removed or records a failure.
3. The VM finalizer is removed.
4. Kubernetes garbage collection removes KubeVirt-owned generated claims.

KubeVirt never deletes direct claims. It only removes the VM reservation from
them.

Managed claim provisioners remain responsible for managed-claim finalizers and
generated-claim cleanup as defined by VEP-300.

### ResourceClaim Spec Immutability

Kubernetes defines `ResourceClaim.spec` as immutable. KubeVirt must not update
the spec of a direct claim or an allocated generated claim in place.

If a VM template change would change the desired spec of a generated claim, the
controller must:

- detect the difference;
- report a clear condition and event;
- replace the claim only after it is no longer allocated or reserved; or
- require an explicit reallocation operation.

Changing only `persistWhenStopped` does not change the ResourceClaim spec.

### Controller Responsibilities

#### Virt-controller

Virt-controller is responsible for:

- resolving direct claim names;
- creating claims from VM-scoped ResourceClaimTemplates;
- rendering concrete claim names into launcher Pods;
- adding and removing VM reservations;
- managing the VM deletion finalizer;
- reporting claim readiness and reservation errors.

Virt-controller does not generate managed claim specs.

#### Managed Claim Provisioner

The managed claim provisioner is responsible for:

- watching VM-scoped managed claim declarations;
- generating the ResourceClaim spec;
- creating the VM-owned ResourceClaim;
- maintaining generated-claim labels and ownership;
- handling managed-claim-specific finalizers and recovery.

It is not responsible for adding or removing VM reservations.

#### Kubernetes DRA Scheduler and Kubelet

Kubernetes remains responsible for:

- allocating ResourceClaims;
- adding and removing Pod consumer references;
- enforcing reservation limits;
- making allocated devices available to the launcher Pod.

### Validation

The validating webhook enforces:

1. Exactly one of `resourceClaimName`, `resourceClaimTemplateName`, or
   `managedClaimProvisionerName` is set.
2. `persistWhenStopped` is only accepted for a claim declared in a VM
   template.
3. Direct claims and ResourceClaimTemplates are in the VM's namespace.
4. Claim names are unique within the VM template.
5. A managed claim provisioner exists and supports VM scope.
6. Every managed claim entry is referenced by at least one device declaration.
7. A standalone VMI cannot request VM-scoped persistence.
8. A VM-generated VMI does not independently change the VM-scoped claim
   source or persistence policy.

### RBAC

Virt-controller requires permissions to:

- get, list, and watch ResourceClaims;
- get, list, and watch ResourceClaimTemplates;
- create generated ResourceClaims;
- update the ResourceClaim status or binding subresource used for
  `reservedFor` on the supported Kubernetes version;
- update VirtualMachines for finalizer management;
- emit events.

Virt-controller must not require delete permission for direct claims.

Managed claim provisioners require the permissions defined by VEP-300,
including access to VM templates, standalone VMIs, ManagedClaimProvisioners,
and ResourceClaims.

### Security Considerations

Direct claim references are an explicit capability of a VM in the same
namespace. KubeVirt does not adopt the claim or modify its spec, but it does
write the VM consumer reference into claim status. Namespace RBAC remains the
boundary for who may create VMs and claims.

Cross-namespace claim references are rejected.

Controllers must verify claim ownership before adopting generated claims and
must never overwrite a generated claim owned by another VM.

### Live Migration

VM-scoped DRA allocations are node-specific and are not live-migratable by
this VEP. VMs using VM-scoped DRA claims must be marked as not live-migratable
unless a future DRA-aware migration design provides equivalent guarantees.

## API Examples

### Direct Claim

The user creates the claim separately:

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: gpu-for-vm
spec:
  devices:
    requests:
    - name: gpu
      exactly:
        deviceClassName: example.com/gpu
        count: 1
```

The VM references it once:

```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: gpu-vm
spec:
  template:
    spec:
      resourceClaims:
      - name: gpu
        resourceClaimName: gpu-for-vm
        persistWhenStopped: true
      domain:
        devices:
          gpus:
          - name: gpu0
            claimName: gpu
            requestName: gpu
```

### ResourceClaimTemplate

```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: gpu-vm
spec:
  template:
    spec:
      resourceClaims:
      - name: gpu
        resourceClaimTemplateName: gpu-template
        persistWhenStopped: true
      domain:
        devices:
          gpus:
          - name: gpu0
            claimName: gpu
            requestName: gpu
```

KubeVirt creates a VM-owned concrete ResourceClaim from `gpu-template` and
places that concrete claim name into the launcher Pod.

### Managed Claim

```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachine
metadata:
  name: aligned-gpu-vm
spec:
  template:
    spec:
      resourceClaims:
      - name: aligned-devices
        managedClaimProvisionerName: gpu-default
        persistWhenStopped: true
      domain:
        devices:
          gpus:
          - name: gpu0
            claimName: aligned-devices
            requestName: gpu
```

The VEP-300 provisioner creates the VM-owned concrete claim. The user does not
add a second entry to the VMI.

### Standalone VMI

```yaml
apiVersion: kubevirt.io/v1
kind: VirtualMachineInstance
metadata:
  name: standalone-vmi
spec:
  resourceClaims:
  - name: gpu
    resourceClaimName: gpu-for-vmi
  domain:
    devices:
      gpus:
      - name: gpu0
        claimName: gpu
        requestName: gpu
```

This remains VMI-scoped and is not affected by VM-scoped persistence.

## Alternatives

### Separate VM ResourceClaimTemplate List

Add a second VM-level list that declares claims to create, while also adding a
matching claim reference to the VMI template.

Rejected because it requires duplicate user configuration and creates two
sources of truth. The existing claim entry in the VM template already provides
the logical name, source, and lifecycle policy.

### Add Persistence Only to Template-Backed Claims

Rejected because direct and managed claims would require separate behavior and
would not receive the same restart guarantees.

### Let Each Claim Type Implement Persistence

Rejected because reservation updates, conflict handling, VM deletion cleanup,
and finalizers would be duplicated across multiple controllers.

### Keep ResourceClaimTemplate References in the Launcher Pod

Rejected because a Pod-generated template claim is tied to Pod lifetime. A
VM-scoped template claim must first become a stable direct ResourceClaim.

### Let Virt-controller Generate Managed Claims

Rejected because VEP-300 assigns claim generation and provisioner-specific
device policy to managed claim provisioners. Virt-controller should only
resolve and render the generated claim name.

### Use an Anchor Pod

Rejected because an anchor Pod adds a second workload, complicates scheduling,
and makes VM deletion and failure handling harder. The VM consumer reference is
the Kubernetes-native mechanism for retaining the allocation.

### Single Allocation Policy

Instead of exposing separate persistence fields such as
`persistWhenStopped` and `persistOnRestart`, define one user-facing
`allocationPolicy`:

```yaml
resourceClaims:
- name: gpu
  resourceClaimName: gpu-claim
  allocationPolicy: WhileRunning
```

Possible values could be:

- `Persistent`: retain the allocation across restart and stop.
- `WhileRunning`: retain it across restart, but release it when stopped.
- `Ephemeral`: release and reallocate it on restart or stop.

This API describes how long the user wants the allocation retained without
exposing internal VMI or Pod lifecycle terminology. It is an open design
consideration; the final API should be selected after user and SIG review.

## Scalability

- Each VM contributes at most one reservation per VM-scoped claim.
- `ResourceClaim.status.reservedFor` has a Kubernetes-defined maximum number
  of entries. A VM normally contributes one entry, so this design does not
  introduce a per-restart accumulation of consumers.
- The number of generated claims is proportional to the number of VM claim
  entries and device declarations.
- Reconciliation must be idempotent and use live reads or conflict retries for
  ResourceClaim status updates.
- VMs without VM-scoped claims incur no additional claim-status updates.
- No anchor Pods or polling loops are required.

## Update/Rollback Compatibility

- The feature is gated behind `PersistentDRAClaims` and is disabled by
  default during alpha.
- Existing standalone VMI claims are unchanged.
- Existing direct VM claim references remain valid; they gain VM reservation
  behavior only when declared in a VM template with the feature gate enabled.
- The initial VEP-344 `VirtualMachineSpec.resourceClaimTemplates` API is
  replaced by the claim-entry API in this design. Because the feature is
  alpha and not a released stable API, the change is intentionally breaking
  before implementation is finalized.
- A rollback must leave generated claims and reservations safe. A controller
  version that does not understand VM reservations must not delete or mutate
  them without first releasing the VM reservation.
- Changes to an allocated ResourceClaim spec require explicit reallocation;
  they are not silently applied during a VM update.

## Functional Testing Approach

### Unit Tests

- Validate mutual exclusion of direct, template, and managed sources.
- Validate that `persistWhenStopped` is rejected for standalone VMIs.
- Validate claim source resolution for all three source types.
- Validate deterministic generated claim naming and owner verification.
- Validate that VM-template claims are not processed as independent VMI claims.
- Validate reservation merge behavior and conflict retries.
- Validate that direct claims are never deleted or spec-mutated.
- Validate generated claim replacement is blocked while allocated or reserved.

### Integration Tests

- Start a VM with a direct claim and verify the VM appears in `reservedFor`.
- Recreate the VMI and verify that the same claim and allocation are reused.
- Stop with `persistWhenStopped: false` and verify that the VM reservation is
  removed.
- Stop with `persistWhenStopped: true` and verify that the VM reservation
  remains.
- Start again after a non-persistent stop and verify that the claim may be
  reallocated.
- Create a VM from a ResourceClaimTemplate and verify that the Pod references
  the concrete VM-owned claim.
- Create a VM with a managed claim and verify that only one VM-owned claim is
  generated.
- Delete the VM and verify that its reservation is removed before finalizer
  completion.
- Verify that direct claims survive VM deletion.

### End-to-End Tests

With a real DRA driver:

- allocate a GPU or host device to a VM;
- restart the VM repeatedly;
- verify that the claim remains allocated and the device identity is stable;
- stop and restart with both persistence policies;
- verify that a second VM cannot acquire a retained allocation;
- verify that deletion releases the device.

Tests must also cover the allocation-to-reservation race and verify that
reservation failures are surfaced and retried.
